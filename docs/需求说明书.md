# 接口自动化测试 Agent — 需求说明书

> 版本:v0.1(待评审)
> 日期:2026-10-03
> 状态:评审中

## 1. 背景与目标

### 1.1 背景

接口自动化测试的常规流程——分析接口、设计用例、编写 pytest 脚本、自测、出报告——工作量大且高度模板化。使用通用 coding agent(如 pi)虽可完成,但每次都要人工引导、重复交代规范,不方便、不快捷。

本项目的目标:做一个**面向接口自动化测试的专用 Agent**,把"生成用例 → 人工评审 → 生成脚本 → 自测 → 报告"固化成一条带质量门禁的流水线,同时通过 **用户自定义 Skill** 适配各公司不同的用例规范。

### 1.2 目标

- 输入一个项目目录(可选:一段版本需求),产出:接口清单 → 测试用例文档(Excel + Markdown)→ pytest 自动化工程 → 自测通过的运行结果 → Allure HTML 测试报告。
- 两个必须的人工评审点:① 接口定位结果评审;② 测试用例评审。其余环节自动完成。
- 用例的**设计方法**(等价类/边界值/场景法/因果图怎么用)和**文档规范**(编号、字段、格式)由用户 Skill 定义,不同公司可直接复用本 Agent。

### 1.3 非目标(v1 不做)

- Web UI / 图形界面
- 对接用例管理平台(禅道/TestLink 等,导出格式留作扩展点)
- 非 HTTP 接口(Dubbo/gRPC/消息队列)
- CI 平台插件(但产物可被 CI 调用)

## 2. 用户与使用场景

**目标用户**:测试工程师 / 测开(常兼开发),熟悉自己项目的业务与接口。

| 编号 | 场景 | 说明 |
| --- | --- | --- |
| S1 | 全量初建 | 项目从未有接口自动化,Agent 扫描全项目接口,生成整套用例与脚本 |
| S2 | 版本迭代 | 项目已迭代多版,用户给出**本版本需求**(文档或文字),Agent 定位需求相关接口,**只**为这部分设计用例 |
| S3 | 规范接入 | 公司有自己的用例规范(等价类怎么分、编号怎么编),以 Skill 形式接入,Agent 按规范产出 |

**关键认知**(来自用户):测试开发者既是测试也是开发,最清楚需求对应哪些接口。Agent 定位接口可能找错/找漏,所以接口定位必须人工评审。

## 3. 核心业务流程

```
┌────────┐   ┌──────────────┐   评审点1   ┌──────────────┐   评审点2   ┌──────────────┐
│ 启动    │ → │ 需求理解与     │ → 【停下】→ │ 用例设计       │ → 【停下】→ │ 自动化脚本生成 │
│ CLI    │   │ 接口定位       │   用户确认   │ (Skill 驱动)  │   用户审核   │   (pytest)   │
└────────┘   │ 接口清单/映射  │   接口映射   │ Excel+MD 文档 │   可改可增   └──────┬───────┘
             └──────────────┘             └──────────────┘                    │
                                                                                 ▼
                                                       ┌──────────────┐   ┌──────────────┐
                                                       │ Allure HTML   │ ← │ Agent 自测    │
                                                       │ 测试报告       │   │ 运行+修复循环  │
                                                       └──────────────┘   └──────────────┘
```

各环节说明:

1. **启动**:CLI 指定项目目录(或子模块);可选提供版本需求(文件或文字)。不给需求则走全量模式(S1)。
2. **需求理解与接口定位**:Agent 识别项目技术栈与业务结构,**不写死语言解析器**(Java controller、Python route、Go handler 等由 LLM 识别),把"需求点 → 相关接口"整理成映射清单(含理由与置信度);全量模式则产出接口清单。
3. **评审点 1**:用户确认/修改/增删接口映射。确认后作为用例设计范围基线。
4. **用例设计**:按用户的**用例设计 Skill**(等价类、边界值、场景法、因果图在本公司怎么用)与**用例文档 Skill**(用例编号规则如"项目-模块-序号"、字段定义、格式)生成用例,输出 Excel + Markdown,Agent 停下。
5. **评审点 2**:用户直接在文件上修改/增删用例,改完确认;Agent 以修改后的文件为最终基线回读。
6. **自动化脚本生成**:基于评审后的用例生成 pytest 自动化工程(数据驱动、公共封装、allure 埋点),用例与脚本可双向追溯。
7. **Agent 自测**:Agent 检测/拉起被测服务,运行生成的测试;失败则归因(脚本缺陷 → 修脚本 / 用例期望错 → 修期望 / **疑似被测系统缺陷 → 不修,标记上报**),循环直到可运行,保证交付的代码本身没有运行问题。
8. **报告**:pytest 运行产出 Allure results,调用本机 allure CLI 生成 **HTML 报告**(v1 仅 HTML)。

## 4. 功能需求

优先级:P0=v1 必须,P1=v1 尽量,P2=后续。

| 编号 | 需求 | 优先级 | 验收标准 |
| --- | --- | --- | --- |
| FR-1 | CLI 接入:命令行工具,指定项目目录/模块,支持需求输入 | P0 | 一条命令启动全流程;`--help` 完整 |
| FR-2 | 需求输入:v1 直接输入需求文本;需求加载抽象为 `RequirementLoader` 接口,按扩展名分发实现(txt/md/word 等后续按需接入,v1 不实现) | P0 | 文本需求可进入定位流程;`--requirement` 传入不支持的格式时给出明确提示 |
| FR-4 | 需求理解与接口定位:需求模式(需求→接口映射,含理由/置信度)与全量模式(接口清单);语言无关,LLM 识别技术栈;**同时识别并记录项目响应约定**(统一信封结构、业务码语义、异常处理器),供用例预期和脚本断言使用 | P0 | 对 demo 项目,给定一段迭代需求,能定位到正确接口集合;对 jmeter-demo(Java)能识别 controller 接口与 200+业务码约定;清单输出为可评审文件 |
| FR-4 | 评审点 1(接口映射):停下等待用户确认;用户可修正;修正结果回读为基线 | P0 | 未确认前不进入用例设计;修改被采纳 |
| FR-5 | Skill 体系:支持用户自定义两类 Skill——①用例设计规范(case-design)②用例文档规范(doc-format);约定目录放置,Agent 自动加载;内置默认 Skill 可被覆盖 | P0 | 更换 Skill 后,产物编号规则、字段、设计方法应用方式随之变化 |
| FR-6 | 用例设计:按 Skill 应用等价类、边界值、场景法、因果图/判定表;字段(编号、标题、步骤、预期、优先级、实际结果等)以 Skill 为准 | P0 | 每个接口至少 1 条 P0 用例;四种方法在产物中可辨识 |
| FR-7 | 用例文档输出:Excel(.xlsx)+ Markdown 双格式;评审点 2 停下;用户改后文件可回读 | P0 | 用户修改 Excel 中的预期值后,后续脚本按修改后的预期生成 |
| FR-8 | 自动化脚本生成:pytest 工程,数据驱动,基于评审后用例,用例↔脚本可追溯(用例编号出现在脚本与报告中) | P0 | 生成的工程结构完整、有 README、可独立运行 |
| FR-9 | Agent 自测:自动检测/拉起被测服务→运行 pytest→失败归因三分类(脚本/期望/疑似缺陷)→修复循环(有限轮数)→保证代码可运行 | P0 | demo 项目上生成的脚本最终运行通过,或明确上报疑似缺陷 |
| FR-10 | 测试报告:allure-pytest 埋点 + 本机 allure CLI 生成 HTML 报告;启动时环境自检(allure 缺失给出安装指引) | P1 | 运行结束给出可打开的 HTML 报告路径 |
| FR-11 | 会话状态与断点续跑:评审点停下落盘,用户处理后可 resume;全过程日志可追溯 | P0 | 任意评审点中断后,resume 能从断点继续且不重复提问 |
| FR-12 | LLM 接入:OpenAI 兼容接口(base_url / api_key / model,配置文件或环境变量) | P0 | 支持至少 DeepSeek / GLM / OpenAI 任一家跑通全流程 |

## 5. 非功能需求

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| NFR-1 | 可复现 | 相同输入 + 相同 Skill,产物结构稳定,文档可 diff |
| NFR-2 | 成本可控 | LLM 调用有预算/轮数上限;扫描与定位结果缓存,避免重复调用 |
| NFR-4 | 兼容性 | Windows 优先(macOS/Linux 不设障碍);Python ≥ 3.11 |
| NFR-5 | 安全提示 | 代码与需求会发送给所配 LLM API,文档中明确提示 |
| NFR-6 | 可观测 | 全程日志(LLM 决策、工具调用、修复过程)落盘,便于审计 |

## 8. 评审决议记录(2026-10-03,已确认)

1. **评审载体**:仅生成 Excel / Markdown 文件,不对接禅道等任何用例管理平台。
2. **需求输入**:v1 直接输入需求文本;加载逻辑抽象为 `RequirementLoader` 接口,按扩展名分发,后续按需实现 txt/word 解析。
3. **响应约定**:不做 Skill 配置项。每个项目的信封结构/业务码规范不同,由 Agent 在扫描阶段**从项目代码中读取**(如统一异常处理器、响应包装类、controller 返回结构),作为用例预期与断言生成的依据。
4. **Allure**:本机已安装 2.46.1,路径 `D:\code\ceshi\componentllure-2.46.1in`;Agent 支持 `allure_home` 配置项与自动探测。
5. **验收项目**:FastAPI demo(完整链路验收)+ `jmeter-demo`(Java Spring,扫描定位验收,环境具备 Maven 3.9.6 + JDK 1.8,可尝试完整链路)。
