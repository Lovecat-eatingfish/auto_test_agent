# 接口自动化测试 Agent — 方案设计

> 版本:v0.1(待评审)
> 日期:2026-10-03
> 对应需求:[需求说明书](./需求说明书.md) v0.1

## 1. 技术底座

| 项 | 选型 | 说明 |
| --- | --- | --- |
| Agent 框架 | `pi-coding-agent-python-sdk` (0.4.3) | 按用户指定;agent 循环、工具、Skill、Hook、事件订阅全部复用 SDK |
| LLM | OpenAI 兼容接口 | DeepSeek / GLM / OpenAI 等,经 `ModelSection(api="openai-completions", base_url, api_key_env)` 配置 |
| 运行环境 | Python ≥ 3.11 + Node.js ≥ 18 | 本机均已满足(3.11.15 / v22.22.2) |
| 测试栈(生成的) | pytest + requests + allure-pytest | 报告用本机 allure CLI 生成 HTML |
| 用例文档 | openpyxl(.xlsx)+ Markdown | 双格式输出与回读 |
| 配置 | YAML(`agent.yaml`)+ 环境变量 | LLM、被测服务地址、启动命令、测试账号 |

**已验证的 SDK 关键能力**(本机安装后确认):

- `create_agent_session / create_agent_session_from_config`:创建会话,`session.prompt()` 驱动内部 agent 循环,`session.subscribe()` 订阅事件做进度输出。
- `ToolDefinition(name, label, description, parameters=JSONSchema, execute)`:注册 Python 自定义领域工具。
- `SkillsSection(paths=[...])`:从本地目录加载用户自定义 Skill。
- `HooksConfig` + PreToolUse `ToolBlockDecision`:工具调用拦截护栏(禁越界写文件、禁危险命令)。
- `ToolsSection(allow=[...])`:按阶段裁剪内置工具(read/write/edit/bash/grep/find/ls)。

## 2. 总体架构:阶段状态机(外循环)× Pi Session(内循环)

```
代码控制:外循环 = 阶段状态机(强制门禁、落盘、续跑、预算)
LLM 驱动:内循环 = 每阶段一个 pi session(LLM 决定调哪些工具、迭代几轮)
```

```
┌──────────────────── 外循环:Pipeline / 阶段状态机(纯代码) ────────────────────┐
│                                                                              │
│  P0 环境自检 → P1 扫描定位 ──▶【门禁1:人审接口】──▶ P2 用例设计 ──▶【门禁2:人审用例】│
│                                                        │                     │
│                                                        ▼                     │
│                          P3 脚本生成 → P4 自测修复循环 → P5 Allure 报告 → 收尾  │
│                                                                              │
│  每阶段:构建 HarnessConfig → create_agent_session → prompt(阶段任务+Skill)    │
│          → 订阅事件打进度 → 结果落盘 state.json → dispose                     │
└──────────────────────────────────────────────────────────────────────────────┘
```

**为什么外循环用代码而不是 LLM 决定**:两个评审点是用户的硬性要求,必须"确定性停下";阶段状态要落盘支持 resume;成本和失控风险可控。这与 pi 单循环的差别是:pi 的循环作为**内循环**原样保留(LLM 自由使用工具干活),外层流程编排由代码接管。

### 双循环职责表

| 循环 | 执行者 | 职责 | 终止条件 |
| --- | --- | --- | --- |
| 外循环 | 代码(状态机) | 阶段推进、门禁检查、状态落盘、预算控制 | 全阶段完成 / 用户中止 / 预算耗尽 |
| 内循环(P1/P2/P3) | pi session(LLM) | 理解需求、检索代码、定位接口、设计用例、生成脚本 | 阶段工具 `finish(...)` 被调用且产物通过本地校验 |
| 内循环(P4 修复) | pi session(LLM) | 失败归因三分类,有限修复 | 全绿 / 轮数上限(2)/ 疑似缺陷上报 |

## 3. 阶段详细设计

### P0 环境自检(纯代码,无 LLM)

检查:Python/Node 版本、LLM 配置(base_url/key/model)、allure CLI 是否可用(FR-9,缺失时告警并给安装指引,不阻断前序阶段)、被测目录存在性。结果写入 `state.json`。

### P1 扫描与定位(内循环 ①)

**输入**:项目目录、需求文本(可选)。
**会话工具**:内置 `grep/find/read/ls` + 自定义工具:

| 自定义工具 | 作用 |
| --- | --- |
| `record_endpoints(endpoints[])` | 结构化登记发现的接口(方法/路径/所属模块/参数摘要/与需求关联度/理由) |
| `save_interface_review(markdown)` | 产出评审文件 `01_接口清单与需求映射.md` |
| `finish(summary)` | 结束阶段(仅当评审文件已保存) |

**系统提示要点**:语言无关的接口识别指引(Java:controller 注解;Python:路由装饰器;Go:handler 注册…);"迭代模式"下先解析需求点,再逐点检索定位,每条映射必须给出**理由与置信度**,宁可多报候选交给人审,不许漏报;同时识别项目**响应约定**(统一信封结构、业务码语义、异常处理器如 @RestControllerAdvice / FastAPI exception_handler),写入 `state.response_convention`。

**产出**:`out/01_接口清单与需求映射.md`(全量模式:纯接口清单)。

**门禁 1**:CLI 交互确认(`y` 继续 / `e` 编辑文件后回读 / `n` 中止)。用户编辑后的文件重新解析进 `state.json`,作为用例设计范围基线。

### P2 用例设计(内循环 ②,Skill 驱动)

**输入**:P1 评审后的接口基线 + 两个用户 Skill 全文。
**会话工具**:内置 `read/grep`(允许翻被测代码看业务规则)+ 自定义工具:

| 自定义工具 | 作用 |
| --- | --- |
| `save_module_cases(module, cases[])` | 保存某模块用例;**本地校验器**先跑:编号符合 doc-skill 的 `case_id_pattern`、字段齐全、每接口≥1 条 P0、四种方法可辨识;不合规→错误信息打回重交 |
| `finish(summary)` | 全部模块保存后结束 |

**产出**:`out/02_测试用例.xlsx` 与 `out/02_测试用例.md`(双格式同源,均由 `cases.json` 生成)。

**门禁 2**:停下提示用户审核,用户可直接改 Excel/MD;确认后回读文件 → 与 `cases.json` 对比合并 → 更新基线。Excel 回读按固定列序 + 容错(空行跳过、列名模糊匹配),解析失败则报错并保留原文件。

### P3 自动化脚本生成(确定性,无 LLM)

**输入**:评审后的用例基线(含机器可执行字段:请求方法/路径/参数/断言)+ 被测服务配置。
**生成方式**:实现阶段决策 —— 用例层脚本也由**确定性代码生成**产出(数据驱动 + 通用执行器),
不经过 LLM。理由:用例基线在门禁 2 已经人审定稿,脚本只是基线的机械映射,
确定性生成 100% 可复现、零幻觉、零成本;场景链(含 $stepN 引用)由通用执行器解释执行。
P1/P2/P4 三个需要理解与判断的阶段仍由 LLM 驱动。

生成的 pytest 工程结构(输出到 `out/testframe/`):

```
testframe/
├── pytest.ini            # allure_results 目录、marker
├── requirements.txt      # pytest, requests, allure-pytest, pyyaml
├── config.yaml           # base_url、超时、测试账号、登录接口
├── conftest.py           # api_client / auth_token fixture
├── common/
│   ├── api_client.py     # requests 封装:日志、token、重试
│   └── assertions.py     # 状态码/业务码/字段断言
├── data/                 # 数据驱动 yaml(与用例编号一一对应)
└── testcases/
    └── test_<模块>.py     # @allure.feature/story/severity,用例编号入 allure.id
```

**可追溯性**:每条用例的编号写入测试函数参数 id 与 `@allure.title`,报告与文档可对上。

### P4 自测与修复循环(内循环 ④)

1. 服务拉起:优先探测 `--base-url` 已在监听;否则按配置 `app_cmd` 子进程拉起,健康检查就绪(超时 30s)。
2. 安装生成工程依赖(venv 内),执行 `pytest --alluredir=allure-results`。
3. 失败归因(LLM,输入=失败用例的请求/期望/实际响应/错误栈):
   - **脚本缺陷** → 修生成工程代码
   - **用例期望错** → 修 data/期望(同步回写用例文档"实际结果"列)
   - **疑似被测系统缺陷** → **不修**,标记上报
4. 循环 ≤ 2 轮;结束态 = 全绿 或 "全绿 + N 条疑似缺陷报告"。
5. `allure generate allure-results -o allure-report --clean`,输出 HTML 报告路径。

### P5 收尾

汇总:产物清单、自测结论、报告路径、Skill 命中情况、token 消耗,写 `out/00_总结.md`。

## 4. Skill 体系设计(需求 FR-4)

### 4.1 目录与优先级

```
<项目目录>/.api-test-agent/skills/     ← 用户项目级(最高优先)
~/.api-test-agent/skills/              ← 用户全局级
<agent包内置>/skills/                   ← 内置默认(最低,可被覆盖)
```

同名 Skill 高优先级覆盖低优先级。加载交给 SDK `SkillsSection(paths=[三个目录])`;同时 Agent 自身按 `type` 字段把 Skill 全文注入对应阶段的系统提示。

### 4.2 Skill 文件格式

每个 Skill 一个目录,`SKILL.md` = YAML front matter + Markdown 规范正文:

```markdown
---
name: acme-case-design        # 全局唯一
type: case-design             # case-design | doc-format
description: ACME 公司接口用例设计规范
---

# 等价类应用要求
(公司规范正文:如何划分有效/无效等价类、必填缺失怎么处理……)

# 边界值要求
(取点规则……)

# 优先级定义
P0 = ……;P1 = ……(机读:每接口至少 1 条 P0)
```

```markdown
---
name: acme-doc-format
type: doc-format
description: ACME 公司用例文档模板
case_id_pattern: "^ACME-[A-Z]+-\\\\d{4}$"   # 机读:编号校验
excel_columns: [用例编号, 用例标题, 前置条件, 测试步骤, 预期结果, 优先级, 实际结果]
---

# 用例编号规则
项目码-模块码-四位序号,模块码对照表:……
```

### 4.3 机读约定

front matter 中以小写下划线键声明的字段(`case_id_pattern`、`excel_columns` 等)由**本地校验器/文档生成器**执行,保证 Skill 不只是提示词、规则真正强制生效;正文规范由 LLM 遵循。`case_id_pattern` 缺省时用内置默认 `^<项目码>-[A-Z]+-\\d{3}$`。

### 4.4 内置默认 Skill

- `default-case-design`:等价类(有效类/必填缺失/类型错误/枚举非法)、边界值(min-1/min/max/max+1、长度越界)、场景法(资源 CRUD 链、登录态流转)、因果图(多条件组合判定表,组合数封顶)、P0-P3 定义。
- `default-doc-format`:编号 `项目-模块-三位序号`、固定列序(编号/模块/标题/优先级/设计方法/前置条件/步骤/测试数据/预期结果/实际结果/执行状态/关联脚本)。

## 5. CLI 设计(需求 FR-1)

```
api-test-agent run <project_dir>
    [--requirement-text "本版本需求:..."]   # v1 主入口:文本需求
    [--requirement <文件>]                  # 按扩展名经 RequirementLoader 分发(txt/md 可用,docx v1 报未实现)
    [--out <输出目录>] [--config <agent.yaml>]
    [--base-url URL | --app-cmd "启动命令"] [--test-account user:pass]
api-test-agent resume <session_id>          # 断点续跑(评审点中断后)
api-test-agent skills init [--dir ...]      # 导出内置默认 Skill 供用户修改
api-test-agent skills list
api-test-agent check-env                    # P0 自检单独可跑
```

- `run` 默认交互式:门禁处终端确认;`--non-interactive` 模式下门禁处直接退出并提示用 `resume` 继续(便于脚本化)。
- 包发布形态:标准 Python 包,`pip install -e .` 后提供 `api-test-agent` 命令。

## 6. 状态与数据契约

- `state.json`(`<out>/.session/state.json`):阶段游标、配置快照、接口基线、用例基线、自测结果、预算计数。评审点中断后 `resume` 读取续跑。
- 需求输入:`RequirementLoader` 接口(`load(source) -> RequirementDoc`),注册表按扩展名分发;v1 实现:内联文本 + txt/md 读取,docx 等未实现格式给出明确报错。
- 响应约定:`state.response_convention`(信封结构、成功/失败判定、业务码表),P1 从被测代码识别,P2 用例预期、P3 断言生成均以此为准。
- 核心数据契约:统一使用 `state.json` 中的 dict 结构(Endpoint:endpoints[];TestCase:cases[],含文档字段 + 机器执行字段 request/expected_spec/scenario_steps),由 validators 本地校验。
- 产物目录(`out/`):`00_总结.md`、`01_接口清单与需求映射.md`、`02_测试用例.xlsx|.md`、`testframe/`(生成的工程)、`.session/`(状态与日志)。

## 7. 护栏(Hooks)

| 护栏 | 实现 |
| --- | --- |
| 只许写项目与 out 目录 | PreToolUse hook 校验 write/edit/bash 目标路径,越界 → `ToolBlockDecision(block)` |
| 禁危险命令 | bash 命令黑名单(rm -rf 越界、格式化盘符等) |
| 阶段工具收敛 | 每阶段 `ToolsSection.allow` 只开所需工具 |
| 预算 | state 记录 LLM 轮数/token,超限降级提示并中止内循环 |

## 8. 风险与对策

| 风险 | 对策 |
| --- | --- |
| allure CLI 不在部分终端 PATH(已确认安装于 D:\code\ceshi\component\allure-2.46.1\bin) | 配置项 `allure_home` + PATH + 已知路径三级探测;仍缺失时 P4 明示降级为仅 allure-results |
| pi SDK 版本新(0.4.x) | M1 先做 SDK 集成冒烟(创建会话/工具/Hook/Skill 四项),不通过则调整接入方式(如降级用 `in_process` backend 验证流程) |
| LLM 定位接口找错/漏报 | 映射强制带理由+置信度,门禁 1 人审兜底;提示词要求"宁多报不漏报" |
| Excel 用户改坏格式 | 固定列序+容错解析;解析失败保留现场、给出错误行列 |
| token 成本失控 | 需求模式先行缩小范围;模块级批量设计;扫描结果缓存;预算护栏 |
| 代码外发 LLM | 文档与启动时提示(NFR-4) |
